<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pull-request author → CI runner | An untrusted fork PR causes workflow code to run on GitHub-hosted infrastructure with the repository's default token. |
| CI runner → GitHub Releases API | The release job holds a write-scoped `GITHUB_TOKEN` and uploads user-downloadable executables. |
| GitHub Actions marketplace → workflow | Third-party actions (setup-go, goreleaser-action, golangci-lint-action) execute with the job's permissions. |
| goreleaser → end user | Published binaries are executed directly by users who downloaded them. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-02-01 | Elevation of Privilege | `ci.yml` trigger and token scope | high | mitigate | `ci.yml` uses `pull_request` (fork PRs run without repository secrets), never `pull_request_target`, and declares a top-level `permissions: contents: read` so no CI job can write to the repo, releases, or packages (Task 1). |
| T-04-02-02 | Information Disclosure | `GITHUB_TOKEN` exposure across release steps | high | mitigate | The token is supplied only in the `env:` block of the single goreleaser-action step; no `run:` step in `release.yml` echoes it, and no other job in either workflow receives write scope (Task 2). |
| T-04-02-03 | Tampering | Third-party GitHub Actions resolving to a moving ref | medium | mitigate | Every action is pinned to an explicit major (`actions/checkout@v5`, `actions/setup-go@v5`, `goreleaser/goreleaser-action@v7`, `golangci/golangci-lint-action@v7`) and the golangci-lint tool version is pinned to an exact patch (`v2.7.2`) rather than left floating (Tasks 1-2). |
| T-04-02-04 | Tampering | Published release assets substituted or truncated in transit | medium | mitigate | `checksum.name_template: checksums.txt` publishes a manifest covering every artifact, so a user can verify a download against the release's own checksum file (Task 2). |
| T-04-02-05 | Spoofing | A non-semver or moving tag triggering an unintended release | medium | mitigate | `on.push.tags` matches only `v*.*.*` (D-11), so a lightweight or moving tag such as `nightly` starts no release run (Task 2). |
| T-04-02-06 | Tampering | CGO reintroduced for a subset of targets, producing a glibc-linked artifact | high | mitigate | A single `builds:` entry carries `env: [CGO_ENABLED=0]` with no per-target override, verified structurally by the Task 2 gate and, where the tool is available, by `ldd` on the Linux artifact (DIST-03). |
| T-04-02-07 | Repudiation | Release provenance unclear for a downloaded binary | low | accept | `-X main.version={{.Version}}` stamps the tag into `alturd --version`, and `-trimpath` removes build-host paths. Cryptographic signing/attestation (cosign, SLSA provenance) is not in DIST-01/02/03 scope and is not added unrequested. |
| T-04-02-SC | Tampering | goreleaser and golangci-lint binaries installed at CI time | high | mitigate | Both are installed by their pinned official actions from their vendors' own release channels; goreleaser is pinned via `version: '~> v2'` and golangci-lint to an exact patch. No `npm`, `pip`, or `cargo` package manager is used anywhere in this plan, so the package-legitimacy checkpoint protocol does not apply; 04-RESEARCH.md §Package Legitimacy Audit records no `[ASSUMED]`, `[SUS]`, or `[SLOP]` verdicts for this phase. |
</threat_model>
