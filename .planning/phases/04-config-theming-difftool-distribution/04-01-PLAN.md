<objective>
Create the `internal/config` package and make alturd's key dispatch data-driven, so a TOML
config file can rebind any of the ten global actions and strict validation rejects a bad
config before the TUI starts.

Purpose: CONFIG-01 and CONFIG-02 are the foundation the rest of Phase 4 sits on — the
theme key (Plan 03) is decoded by the same loader, and the key-dispatch refactor is the
architectural seam that must be proven end-to-end before anything else is layered on.
This plan LEADS the phase with a tracer slice (Task 2) that wires TOML file → decode →
keymap → bubbletea dispatch on one real path, then expands validation out from it.

Output: `internal/config/{config,keybindings}.go` plus tests, a keymap-driven
`internal/tui/model.go` normal-mode dispatch, and a `--config` flag on `rootCmd`.
</objective>

<assumption_delta_decision>
The `assumption-delta` scan on this phase returned `detected: true`, signal kind `chosen`
("The application is fully configurable via TOML"). The identity-model question is
derived→chosen: values that were previously *derived* from source (the ten hardcoded key
literals in `handleKey`) become *chosen* by the user.

**Decision: promote (not add-alongside).** The ten default key strings are demoted from
"the dispatch table" to "one source feeding the single resolved `Keymap`". There is no
second config-aware branch running alongside a hardcoded branch: `handleKey` resolves every
normal-mode key through exactly one `Keymap.Lookup` call. Promotion is preferred here
because an add-alongside shape (defaults switch + override switch) would let a rebound key
and its former default both fire, which is exactly the "silent last one wins" behaviour D-02
forbids. Advisory checkpoint — recorded, non-blocking.
</assumption_delta_decision>

      <pros>Reads closer to CLI flag naming; identical validation story to the snake_case option.</pros>
